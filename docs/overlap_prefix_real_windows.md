# Does exact raw-prefix reuse survive real adjacent-suffix order?

Proposed **partial 100 MB study**, neither a full pass nor a target builder. The [generated equality mechanism](../gates/receipts/raw-prefix-proof-fixture/) had 99.968% logical savings on exact twins, but on the mutated mosaic even 47% fewer compared bytes did not improve loop time. Consecutive suffixes in sorted order need not keep useful displacement intervals in cache. Test on the authenticated `100,000,503`-byte input and the already certified reference; no 100 GB text or product. Apply flat raw suffix order including unique END; do not substitute a document-clipped suffix order for the builder's global rows.

**Bounded true rank windows, no SA/LCP spool.** Fix 16 disjoint equal-rank strata of the `100,000,504` true rows. Before inspecting data, use `mix(0xF6B8D2A4+i)` to choose the first rank of 65,536 consecutive edges (plus one predecessor) inside each stratum. A histogram of *all* three-code prefix keys (`END=0`, byte `c→1+c`, zero pad after EOF) locates complete covering key ranges and their exact preceding row counts. Scan raw bytes a second time to collect only the matching positions. Refuse BEFORE allocating positions on overlapping covers or >4,194,304 candidate positions, not after sorting an unexpectedly large tie. Sort those complete ranges by the entire raw suffix. Every selected edge is therefore truly adjacent: other keys precede/follow the whole range. Neither filtering isolated positions nor independently sorting small chunks of the *text* would preserve this property. Histogram `257³×4` bytes; then free it, use a one-byte per key dispatch map, keep at most 16 MiB positions. Two raw key scans are not two verified all-row passes. All widths here are the small profile's, not a trial above u32.

In each uninterrupted range derive each adjacent LCP from raw bytes, compare the first unequal byte/END, then run [the exact interval proof](overlap_raw_prefix_intervals.md) with both 256×4 and 4096×4 caches at `h≥1024`. Never mix file identities or carry a proof across unsampled rank gaps. Compare 32,768 initially cold-table edges vs the following 32,768 warmed-table edges per window; **this is proof-table cold/warm, not page-cache cold/warm**. Report lengths served by actual comparisons and certified hits, escape/deep incidence, displacements ≥1 MiB and distinct start pages. Candidate raw-work caps 32 GiB comparator requests, 2 GiB direct-LCP chunk requests (plus scalar mismatch location); cooperatively stop. The ordering/selection oracle is not part of any product or phase timer. Full verification of sorted rows/last rank remains mandatory for a new product.

**Independent spot checks.** Check raw BWT changes at *every* authenticated m12 1024-run boundary inside each window and verify the 1024-change spacing when consecutive boundaries are present. After sorting, compare each fully observed tail position there against the reference m11 cell. A run extending through the last included row is explicitly incomplete, never credited as an anchor. No old positions supplied to `select()` or `order()`. Keep only bounded counters and sparse crosschecks. Generated tests cover the full selector vs a separate direct SA with NUL, proper prefix and EOF cases; fail closed on too much candidate mass, overlapping bins, invalid ranks or work cap.

[Generated selector qualification passed](../gates/receipts/prefix-window-tools/): independent 6,001-row oracle, 1,245 observed edges plus mass/work/overlap refusals. The fixed real-window worker is a separate one-shot arm with one pinned CPU, 256 MiB shared and zero swap, fresh preallocated and hashed input (fsync/private eviction/mincore). The table of 37,742 m12 block starts is incidental scratch; m11 is read for postchecks only. The supervisor samples nested logical and physical file allocations and open descriptors, deduplicates names, refuses a private deleted file/mapping, separates the raw input, and caps auxiliary space at 4 MiB plus 1 MiB for the final controls. No row or LCP output. `io.stat`, if unavailable, is not a disk counter; observer/parent block IO is attributed only. Probe setup and selection are not builder benchmarks.

**Falsifiable signal, not promotion.** Of the 524,288 warmed-table edges, does the 397,312-byte table avoid at least 25% of the *sum of all* claimed equal-prefix lengths, and ≥10% in at least eight of the sixteen windows? Also report small-table results (24,832 B) and the whole observed sample, even if the signal misses. This threshold is for whether real 100 MB window behavior merits wider experiments; it is not a CPU, time or IO win. Compare sample prefix lengths/escape rates with the archived all-row witness. Efficiency may change if the first rank begins inside a different hot set, or the larger corpus changes LCP lengths, skew, eviction and page behavior. No extrapolation to 100 GB's ≥13.79 TB naive-work bound, no verifier change or launch grant. The 100 MB reconstruction itself is not repeated.
