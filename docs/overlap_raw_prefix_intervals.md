# Can an independent raw verifier reuse exact equal bytes?

The [archived 100 GB LCP geometry](../gates/receipts/v10-target-fold-transfer/) gives a **13.79 TB logical lower bound on naive prefix comparisons**, not device IO or a runtime. The brute-force checker is correct. Do not replace it with sampling, fingerprints, producer ranks or the old reference index. Test a narrower claim: in an immutable private raw text, equal bytes already verified on the *same displacement* need not be compared again. No change to any admitted production verifier or sorting profile.

**Certificate.** Canonicalize position pair `(a,b)` to `a≤b`, `d=b−a`. An entry `(d,lo,hi)` means `raw[i]==raw[i+d]` for **every** `i∈[lo,hi)`. A new positive request `[a,a+h)` can skip only its actual overlap with intervals carrying exactly `d`. Compare all remaining gaps with guarded raw memcmp chunks of at most 65,536 bytes. Only after every gap succeeds, insert the entire now-proved interval, coalescing exact overlaps/touching ends, **never** taking the convex hull across an unchecked byte. A mismatch or cancellation cannot install an incomplete proof. Swapping positions preserves equality. The hash chooses a four-way bucket, not equality. Dropping an entry can cause extra work but cannot change the answer. Bound-check before addition/subtraction; input belongs to one fresh cache instance and must not change while it lives. No new proof from another file, comparison with a producer's LCP, or equality of a key/hash. This validates only the claimed equal prefix; strict next-byte/endpoint ordering, predecessor, count/coverage, EOF, independent final rank, hashes and packet holdbacks still belong to the raw verifier.

**[Generated results](../gates/receipts/raw-prefix-proof-fixture/).** Exact duplicates 99.968% logical reuse and lower warm loop time; shorter mutated mosaic 47.16% reuse but slightly *higher* loop time. Correctness and mechanism only. The existing raw checker remains unchanged.

**Mechanism under test.** Fixed 4,096 × 4 entries of three u64s plus 4,096 victim bytes = **397,312 B** of proof table; four local range records, fixed counters and object fields in addition. No row spool or byte-level rank/SA in this subroutine. Skip table lookup when `h<1,024`. For two exact copies of length `M` at fixed displacement, claims starting throughout the copies can cover the same diagonal again and again. Once a suffix of the interval is proved, a shifted claim need only extend its beginning. A single retained diagonal can collapse quadratic repeated work into linear, apart from below-threshold claims. But two suffixes with long common prefixes need not be adjacent when there are other copies, and widely separated access can evict the useful interval. No savings are guaranteed on real suffix streams. Small working sets make cached-vs-direct CPU ratios unsuitable for 100 GB prediction.

**Predeclared generated study.** Build an independent in-memory doubling+Kasai fixture only for ≤180,000 generated bytes, compare identical adjacent prefixes and order endpoints by the direct and cached routines. Two pseudo-random 65,536-byte copies must remove **>95%** of requested raw comparison lengths, while random noise must trigger no long lookup. A mixed mosaic has no hit-rate threshold. Exhaust all two-symbol eight-byte texts and both valid/false prefix claims; refuse a mismatching single-byte hole between two true intervals, malformed extents, and cancelled extensions. A forced two-way/three-diagonal collision must give zero reuse and still be correct. No real text, reused index, target row stream or full-product timing. One CPU/128 MiB/no swap, pinned source snapshot and bounded compiler. Positive cases report successful logical bytes actually sent to memcmp, proven bytes skipped, hits, evictions and warm fixture timings; invalid cases do not infer how many bytes libc examined before returning false. Only if the mechanism survives should a separate bounded *real* access-pattern probe be considered.
