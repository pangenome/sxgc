# Can the small v10 handoff make progress on the target's run lengths?

The [complete real 100 MB pair](../gates/receipts/real-v10-product-100m/) removes the small product-identity blocker. Its rolling emitter spent 211 CPU-s (vs 35 for the resident sorter), while the direct and band trie taps each used ~62 CPU-s. Dropping position files did not make trie computation free. Before spending a larger grant on throughput, test a more basic premise: can six **run-piece** credits and five **row-slice** credits keep the serial sink moving? Larger input does not leave their ratio constant. The consumer's read acknowledgment still cannot be used as durable PRC1 deletion.

**[Observed result](../gates/receipts/v10-target-credits/): five slices stall.** On the target, one 65,536-run piece spans 103,768,030 rows. The lower/upper slice-credit bounds coincide at **395**; three piece credits suffice. This tests a proposed resegmentation of the archived run stream, not the historic tape writer's variable-row slice window. Up to 397 source slices can intersect one loader job; this bounds copies kept in memory, not credits needed on disk. The 100 MB control replayed four/three. Keep both product defaults and all larger launch gates unchanged.

**Fixed metadata-only study.** Use m12 in the exact 100 MB independent product and the earlier 100,000,000,000-byte rehearsal's completed v10 container. Do **not** use an m12 table to manufacture rows, verify the historical whole-container contents, or provide a prebuilt member to a new construction. Only read fixed 64-byte head, 400-byte directory and full m12 (306,720 / 248,999,568 B). Pin each header+directory digest, extent/codec/counts/ranges, both CRCs and unchanged file identity. Pin known small member SHA; record target m12 SHA. Every 1024-run sample must advance by at least 1024 rows, every 65536-run sample must agree with it, and the last sample must leave room for every remaining run. Stream 1 MiB blocks of samples; only three arrays of one u64 per **piece**, not 30.6M Python integers or a full index mapping. One CPU / 128 MiB / zero swap / ≤120 s, bounded output, timing lock, private STOP. No cold or physical device throughput claim. Fixed inputs only; no raw read, sort, producer, finish, large scratch, new 100 GB product or larger lease.

**Prediction / refusal rule.** For the *same* correctly ordered, maximal run stream with no seams, suppose one writer cuts each 65,536 runs and each 262,144 LCP rows. `y[r]` is the row start of run r; before a piece is available the fold can advance through the previous piece less two delayed runs. For a cut at `r`, bracket `y[max(0,r−2)]` between the preceding exact block sample plus one row per subsequent run, and the exact piece start minus one row per trailing run (exact for a sampled target). Count complete and consumed slices with the actual opposite publication order at an internal lookahead vs EOF; count only piece starts *strictly below* the end of the required slice. Use the optimistic frontier for a necessary slice count, pessimistic frontier for sufficient slice/piece credits. Under this serial schedule, a necessary count >5 disproves the small slice window (without a different prefetch/publication protocol); a sufficient count ≤5 alongside ≤6 pieces establishes credit feasibility only. A gap is reported as unproven, not a PASS. The old 100 MB result (4 slices necessary/sufficient, 3 pieces sufficient, 1,126,176 max piece span) must replay. Synthetic schedules include long single runs, all singleton runs, partial and aligned terminal cuts; compare with the independent row-level state machine in `overlap_finish_credits_test.py`.

For one fold `[max(0,prev_end−1), end)` also upper-bound stage rows + 17 × all source rows in whole intersecting slices (1 marker, at most one 16-byte escape/row), including the EOF drain. This is a **logical loader geometry upper**, not allocator/RSS or the actual escape mix. It can be loose; measure before narrowing a real reader's limits. The 100 MB u16 packed LCP range, five disk capacities, 4096 filesystem inodes, 64 KiB/192 KiB logs and granted throughput do not transfer.
