# Does the frozen v8 readiness path actually produce the smaller grid?

**Component prediction, not joint admission.** At `n = 100,000,504` (raw + one virtual END) and `PFCK_SPACING=128`, the unmodified historical executable must produce exactly `floor(n/128)+1 = 781,254` checkpoints in **6,250,072 B** including its 40-byte header. The historical spacing 22 took 36,363,864 B. Neither is an on-disk SXI2 member. The [file-credit study](overlap_finish_credits.md) depends on this exact extent, not a compression ratio.

The original `ext-product-QhQZxU/finish.log` (SHA `75a6e89636bb85e28ddf801f59cf60f0031ed6c0806c1c862819c97c56c19295`) reports Kasai from sorter bands, no walk fallback or seam class, and **zero LCE queries** for both `pile-finish-corpus` and `pile-finish-seam`. Each reports 512 suffix-hash probe charges/5,396 suffix-symbol reads: two suffixes for each of 256 startup self-checks. On that exact path it is not justified to multiply the 509.2 s historical `lce_wall` by `128/22`: that clock contains band-feed/slice waits, not a stream of fingerprint walks. Nor does this prove time or identity at 128. A different stream, seam profile or mode can use the grid substantially more.

`gates/overlap_pfck128_study.sh DEADLINE` was a single-use daytime **readiness-only** instrument. Same 601–1,000 s admission lease as other single 100 MB arms, separate 45 s native deadlines. Fresh published pin, timing lock/known-worker check, fixed input and executable SHAs, fresh fsynced/evicted private copies. `XSA_FINISH_RSS_READINESS_ONLY=1` joins the PFCK builder and codebook histogram then returns *before* opening a piece source or invoking `fp_self_check`. Keep the new PFCK for independent post-close proof. No row producer, bands directory, output directory, ranker, old payload replay or larger dispatch. Refuse an earlier started arm.

* Readiness: 192 MiB shared incl cache and meter, two physical CPUs, no swap; two requested finish threads. The frozen histogram launches eight small jobs, separately from two PFCK workers/eight segments. `LimitFSIZE=6250072` is hard **per file**, useful here because there is one native payload; it is **not** an aggregate finish quota. `LimitDATA=64 MiB`/1 MiB stack and two malloc arenas constrain this startup experiment. RLIMIT_DATA is not a cap on all address space, shared file mappings or total RSS. Do not grant a sweep on this evidence. Account separately for the private raw copy and 16 MiB controls/tools allowance (including the 12,224,128 B private frozen executable), outside any new joint service comparison.
* Separate 128 MiB/one CPU post-close check after private fsync/evict/`mincore`. [`overlap_pfck128_proof.cpp`](../gates/overlap_pfck128_proof.cpp) reads raw blocks **forwards**, applying the independent remap and ascending powers of `B=0x9e3779b185ebca87`. For every grid point verify `H(kT) = sum_j (code+1)*B^j + B^len*H((k+1)T)` modulo 2^64. At the right boundary there is exactly one virtual zero symbol and no other suffix term; include the empty final checkpoint when divisible. Adjacent equations plus the anchored end determine **all** stored u64s uniquely. This checks the actual grid values, not collision freedom or sweep behavior. Native creates the file via parallel segment corrections; the checker has no segment/prefix correction code, suffix array or second full grid. Record separate ready, barrier, proof and SHA clocks, attributed traffic and cgroup peaks. A lack of per-device counters is not zero IO.

Generated tests cover singleton raw, exact 128 boundaries, the 8,192-checkpoint IO seam and malformed headers, extents and values. This probe cannot close the complete downstream scratch/working-set, credit progress or product identity gates.

**Actual exit: FAIL, before the first PFCK byte.** `proc_c9e3`, pin `8ae9959`, [original telemetry and failure receipt](../gates/receipts/pfck128-ready-entry-failure/). Setup passed; metered child died on SIGSEGV (`rc=-11`), empty native log, no PFCK, no OOM, no native STOP. Launcher exited 1 and retained the private files/STOP. The native process's zero *attributed storage* reads do not include the setup copy. The 0.202 s failure observation is **not** a readiness time. For the pinned ELF, `objdump -d --disassemble=main` shows the entry probing `0x21e000` stack bytes in pages and then reserving `0x980` more *before argument dispatch*: **2,222,464 B** plus saved registers, alignment, argv/env and callees, versus the hard **1,048,576 B** limit. Even a one-byte corpus cannot enter `main` at these limits. Worker stack defaults and the initial thread stack are different things. The failed publication is retained, the launcher refuses before source or inputs, and the real grid/identity remains unmeasured. Do not increase the limit and rescore this arm.
