# Parallel 64-bit P1 order — a materialized build stage, not a byte SA

`tools/parse64.cpp` reads **unsigned little-endian 64-bit lexical keys in text order** and publishes a text-order `inverse.u64`. All occurrence coordinates, suffix positions/ranks, group bounds, histogram counts, offsets and strides are u64; size/grant products are checked in u128 before allocating. Zero and `UINT64_MAX` are valid keys. Rank zero is **only** the absent continuation. Neither `max(key)+1` slots nor signed libsais indices are used. The only u32 format reader is the explicitly named compatibility adapter to old banked columns. No full byte-level SA, LCP or triples file is written.

```
g++ -std=c++20 -O3 -Wall -Wextra -Werror -fopenmp xsa/pfp/tools/parse64.cpp -o parse64
parse64 plan M WORKERS
parse64 rank KEYS.u64 NEW_INVERSE.u64 WORKERS ARRAY_GRANT_BYTES STOP_PATH DEADLINE_UNIX
# Legacy lexical IDs -> real unsigned packed-dictionary byte addresses, not made-up high bits:
parse64 lift dictionary.packed parse.u32 NEW_KEYS.u64 K WORKERS ARRAY_GRANT_BYTES STOP_PATH DEADLINE_UNIX
```

Require immutable regular input and a fresh output path under an externally metered grant. Filesystem capacity, swap, CPU quota, cgroup, and time admission are the supervisor's job. Write a private partial, fsync, and publish under the requested name without replacing an existing file. Discard on nonzero exit; the partial may remain as failure evidence.

**Where the parallelism is.** First stably distribute `(key:u64,position:u64)` by varying radix bytes, in parallel: ordered thread/bin prefix sums give disjoint destinations; no per-row atomics. In order of first key, each equal-prefix group receives its starting SA slot + 1 as rank. Partition into work tiles only between complete first keys. At depth h, gather `rank[p+h]` (or END=0) for all still-tied positions **before any rank update**. Independent tiles then order each live group by that second rank and relabel its subgroups, giving exact order to depth 2h. Singleton ranks are final immediately. Each group of size ≥2 has two available link slots in a separate array (end and next group); rebuilding a tile's list only overwrites processed groups, never a following group. Dynamic scheduling across tiles, no merging across tile boundaries. Skew is real: **within one indivisible group `std::sort` is serial**. The log records unresolved mass and maximum group by round. Worst case O(log m) rounds; the data, not the theorem, determines whether this beats an induced sort.

**Proof of output:** for each ordered position `p` check `inverse[p]==slot+1` and all adjacent numeric `(key[p],inverse[p+1] or 0)` strictly increase. This gives permutation and exact lexicographic suffix order by successor induction. A separate single-thread `gates/overlap_parse64_verify.cpp` independently rebuilds the permutation from the *written* inverse column and checks the recurrence against the original numeric keys (or original lexical IDs, explicitly LE width 4). The adapter verifies sorted complete `(raw,EOF)` records, bounds, one tagged final occurrence, then maps dense IDs to their actual record starts. Numeric order of those starts is lexical ID order. Width tests include zero, signed crossings, >2^32, `UINT64_MAX`, cuts, ties, long repeated prefixes, budget and corrupt rank refusal.

**Space on the 100 GB critical path.** Initial radix: `8m` input mapping + `2*16m` entries. Release the spare entry buffer **before** allocating `8m` inverse + `8m` live-group links. Both phases ≤`40m`, plus `4 MiB + 2 MiB/worker` control allowance; account runtime/allocator, system cache and service separately. At the **measured** `m=3,181,334,488`, four workers: **127,265,962,432 B (118.53 GiB)** planned including input, independent of unknown `k`. A `keys.u64` and an `inverse.u64` are each **25,450,675,904 B**. With the old upper bound on packed tape and only those two columns, their simultaneous file payload + 4 MiB is ≤**189,081,559,960 B**. Keeping a redundant legacy `parse.u32` as well can exceed 2N: a new 100 GB front should emit u64 directly or prove retirement before ranking. This is one phase, not a 100 GB grant, consumer lifetime or wall prediction. Next interfaces to widen are the lexical front's text-order assignment records and the aligned/list/range consumers of the rank column. The present row43 wire can already carry the actual 100 GB positions/LCPs, but is not a universal 64-bit wire.

**Measured:** [the fixed 10 GB parse pair](../../gates/receipts/parse64-10g/) passed: 203,696,244 genuine keys above u32; 11.652 s four workers vs 33.759 s one, exact same verified 2,545,315,904-byte inverse. No new whole-product or 100 GB measurement.
