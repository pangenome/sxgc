# Wide position front: shrink the ordering record, not the address space

The [measured direct front](../../gates/receipts/raw64-p1-10g/) spends most of its wall time ordering bins, but at four workers aggregate idle capacity in that loop was only 5.2%. The full cached `(8-byte prefix,8-byte ordinal)` layout and dense start column also need **164.25 GiB incl. input at 100 GB**. This candidate keeps the same dictionary, 64-bit occurrence keys, ordering and fsync boundary. It attacks the live set without adding more threads, an on-disk routing pass, or repeated whole-dictionary walks.

```
front64 plan-pos N M THREADS
front64 pos RAW NEW_DIRECTORY THREADS ARRAY_GRANT_BYTES SCRATCH_BYTES STOP DEADLINE
```

* **One trigger scan.** Assign whole 512-byte blocks of candidate starts to lanes (including all seven bytes of lookahead where needed). Fill disjoint start masks and local exclusive rank anchors; prefix-sum lane totals and add those bases. Visit the set bits to distribute starts into the same 4,096 whole lexical bins. Every possible start belongs to exactly one worker, regardless of a word crossing a lane cut. `ordinal(p)` uses its 64-bit anchor and up to eight popcounts. `following(p)` examines the remaining current + next stripe, then binary searches the monotone anchors over arbitrarily long empty regions. The bitset indexes genuine PFP starts, not approximate matches or sorted output positions.
* **One u64 per sort row.** Store the full absolute start in its required `w=bit_width(N-1)` low bits. Above it cache the next `min(52,64-w)` lexical prefix bits *after* the 12 bits common to the bin. At 100 GB this is **37 position + 27 projected-prefix bits**; no signed field, fixed 32-bit coordinate or 40-bit ceiling. The comparator first checks just those cached prefix bits, **not** the combined integer (the start is not a lexical tiebreaker). On equality compare full leading bytes, actual word spans and the EOF tag. Test projections at `2^32+1`, 100 GB and signed `off_t` maximum; the generator itself guards file/array extents in u128. Addresses on the published wire remain unrestricted u64 within the file.
* **Disjoint publication.** Keep one new-head bit per *sorted* slot padded at bin boundaries so workers never update the same word. Prefix-sum exact record bytes, then write the canonical dictionary simultaneously into disjoint final ranges. Release the raw map **before** allocating `keys.u64`'s memory buffer. Retrace new-head lengths from the trigger bitmap, use text rank to scatter true dictionary addresses, write contiguous keys and publish the closed directory. No raw reread during the scatter; no copy of the dense ordinal column. The extra popcounts and random accesses can cost time: a smaller sort row is not proof of a faster one.

The planned resident upper at four workers is `max(N,8m) + 8ceil(N/64) + 8(ceil(N/512)+1) + 8m + 8ceil(m/64) + 12 MiB`. Control allowance includes ≤32 KiB per-bin word padding (total, not per worker), histograms, meters, buffers and worker allowances. 10 GB: **14,003,919,392 B** vs 17,648,530,632 B for the reference. At actual 100 GB `m=3,181,334,488`: **139,923,425,640 B (130.31 GiB)**, below the illustrative 140 GiB *array* envelope. This is a different concrete implementation from the earlier anchor/displacement design sketch. Cgroup, cache, later stages, concurrent verifier, measured vocabulary and file lifetimes need separate admission.

**One fixed 10 GB challenge, predeclared.** `gates/overlap_front64_pos_study.sh DEADLINE` tests only raw→wide columns. Same private hash/cold setup, four core affinity, 32 GiB shared/20 GiB allowed arrays, zero swap, 420 s front stop and bounded IO, the same independent binary checking against every legacy record/occurrence under 14,000 MiB/1 CPU. Require both native column SHAs to match the completed reference exactly; no need to rerun the rank or the baseline. Evaluate candidate raw→columns against the 122.281 s front clock, **not** the 138.361 s composed rank endpoint. For the layout hypothesis require ≤1.50× wall, ≤0.85× sampled native RSS, ≤1.05× attributed reads and writes, and planned arrays ≤14 GiB at 10 GB. Report full cgroup peak separately because it includes file cache. Publish misses unchanged. Matching SHA and an array estimate do not authorize a 100 GB build.
