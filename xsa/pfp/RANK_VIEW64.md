# Exact aligned LCP and occurrence access from the wide P1 handoff

[`RankView::build`](src/overlap_rank_view64.rs) is the first consumer for native `dictionary.lex64`, text-order `keys.u64` and the one-based `inverse.u64`. It takes borrowed slices, verified text extent, worker count, byte grant and a cooperative stop predicate. It doesn't read the corpus, produce a byte SA, require dense `word:u32` IDs, call signed PLCP, or write another column to disk. It's a **resident reference kernel tested on generated inputs**, not yet the selected emitter or a 100 GB fit.

**Validate once.** Invert the permutation into rank-order occurrence ordinals. In rank order, adjacent `(key, successor_rank or 0)` pairs must strictly increase. Each new head address must be the *next actual record boundary*; require strict `(raw,EOF)` order, full tape coverage and a single terminal record. In text order, check every eight-byte overlap, require EOF only on the last occurrence and prefix-sum owned strides to the supplied `N`. Inputs are assumed to be an authenticated PFP parse, not arbitrary strings that merely overlap. This is not a substitute for validating PFP trigger cuts or raw identity in the front.

**Get a list without building a CSR.** The interval of equal keys in P1 rank order *is* the occurrence list for that word. Since successor rank already breaks ties, no separate per-word scatter, text-position sort, `next` column or dense `loc[k+1]` array is needed. `slots(key:u64)` returns a half-open range of zero-based slots, empty if absent. `get(slot)` returns `(ordinal, key, raw start, successor rank, adjacent aligned byte LCP, predecessor)`. The last owned byte of the preceding word gives the predecessor; use 256 at text position zero. END has rank 0, not a reserved lexical key.

**Parallel token PLCP, byte-aligned result.** In contiguous text-ordinal stripes run Kasai against the ordinal at the preceding parse rank. If z whole words match, the next text-ordinal pair has a known lower bound `z.saturating_sub(1)` by the usual intervening-suffix argument. Start with zero at stripe boundaries: they never depend on another worker's mutable state. Total token extension work is O(m + sum of boundary overhangs), O(workers*m) worst case, **not** a constant-speedup guarantee. Byte LCP for the adjacent aligned starts is `starts[j+z]-starts[j] + common(raw(first unequal words))`. The first differing word comparison is not necessarily constant time. Store the result in **text order**, read it through the existing permutation. A block-of-64 min tree supplies `lce(a,b)` on **one-based ranks**: min over adjacent-LCP slots `[min(a,b),max(a,b))`, either END gives zero, equal nonzero ranks give the remaining suffix length. Finite-tail emission can use this for its tied continuation LCP; no emitter or product phase is run here.

**Costs and next fit decision.** `T + 40m + 8 + 16ceil(m/64) + 4 MiB + 2 MiB/worker` includes mapped native lexical tape `T=U+16k-8`, both 8m input columns and three 8m arrays (rank-to-ordinal, starts incl terminal, aligned PLCP), plus the min tree and controls. The caller must separately admit cgroup/page-cache/allocator and concurrent readers. At the known 10 GB dimensions it's **25,699,557,248 B (23.935 GiB)** at four workers, not a measured peak. At the measured 100 GB m the min tree costs **795,333,632 B**. With only worst-case vocabulary bounds, this reference layout needs up to **278,962,647,872 B (259.80 GiB)** before any suffix ordering or consumers. It cannot be promoted under a hypothetical 140 GiB comparison. All three native *files* could also need **201,802,703,608 B**, exceeding 2N even before margin; admit on measured `k,U` or change their lifetimes. Space next steps are to avoid retaining redundant order columns in the emitting view (sampled ordinals/successor walking, compact starts/PLCP with checked wide access), and budget decoding costs and parallel LCP/order access against a real working set. Do not dispatch the whole builder because a single stage is fast.

**Coverage.** [Fixture receipts](../../gates/receipts/rank-view64-fixtures/) use actual `front64` and `parse64` processes and a separate raw byte suffix sort, not two invocations of the consumer comparing to themselves. Check every aligned start, position, predecessor, successor, rank, lexical range, adjacent LCP and additional RMQs across 1/2/4 consumers. Test bad permutations/recurrences, non-record offsets, truncation, wrong text extent, STOP and grant; arithmetic >u32 is not a physical >2³²-occurrence run. Thirty native handoffs succeeded. A 31st case with dense triggers proves why the 2N gate must be real: 3,969 bytes, 991 occurrences, just 6 distinct words, but 8,046 bytes of wide columns > 7,938 allowed. The first harness wrongly required success; the fixed test requires the independently predicted refusal. No cap change.
