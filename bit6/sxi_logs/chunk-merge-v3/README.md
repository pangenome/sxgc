# Batch BCR chunk merge gate

`bit6/chunk_bcr_merge.cpp` consumes each `SXCR` chunk file once. It expands
its local cyclic BWT in memory, derives LF, finds the row for local SA zero
from a run-head SA sample, and traverses LF to recover its bytes in reverse
cyclic order. It feeds those bytes to the banked dynamic BCR insertion code.
The original corpus is never read by the merge. The chunk front end and the
monolithic reference parser each read the corpus once in their own build.

BCR's `prepend` operation places each new symbol before the existing text.
To preserve the source concatenation `chunk-0 ... chunk-15`, the merge consumes
the **batch files in reverse index order, 15 through 0**. Each batch is a
single measured insertion stage; its symbols are handled in BCR's reverse
order. This differs literally from a request to process chunk files 0 through
15. Feeding them 0 through 15 to this proven primitive would produce a
different corpus, so the exactness gate uses the necessary reverse order.

The `unit-gate.log` differential compares all four files against the direct
BCR frontend on four independent small collections, including periodic
collections. `chunk-header-gate.log` checks coverage of the 16 fragment
chunks. `merge.log` has per-batch insertion walls and the final merge wall;
`merge.time` captures the full process wall and peak RSS. The reference raw
files are regenerated by the PFP parser, level-2 parser, and rpfbwt under
`vendor/chunk-merge-v3/reference/`. `finish_gate.sh` performs four bytewise
comparisons, adapts **the merged raw files** to normalized ri4, and computes
chi once from that merged structure using the reference PFP parse for LCP
queries. `summarize.py` creates the honest table after every gate passes.

Artifacts are private under `vendor/chunk-merge-v3/`; the source and journal
files are in this worktree and must remain unstaged. No O(runs) cross-LCP
merge or speedup is claimed.
