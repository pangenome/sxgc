## Process lessons this session (binding)
 - A 30-minute agent budget is wrong for verification work: three runs finished their code and
   were killed while the GATE was still running. Agents code; the parent runs gates, unbounded.
 - External-cli runners (sol) are opaque and uncontrollable (no steer/resume/toolEvents) and they
   stall asking for a tool they lack. Use them for narrow, self-contained jobs only.
 - No number may come from a wrapper. Everything runs through `xsa build`; the bundle builds and
   hashes every tool; fused_gate.py is out of the run path.
 - Every rung needs a query-position gate, not just chi/closure/decode.

## Update: the front door cannot yet build END-format containers (measured)

`xsa build --tape --input <1 GB> --threads 64 --timeout 3600` on the shipping tree 37f336e
refuses in all three children, for the same reason:

    order-tape   scatter_sort: remap does not preserve byte order
    emit-tape    bin-bwt remap must map 0xf5 to the minimal symbol 0 (the sentinel)
    finish-v2    remap: the end-of-text byte 0xf5 must map to the minimal symbol 0

Cause: chain.rs still passes the LEGACY fixed PRODUCTION_REMAP. The END-format finish requires a
CORPUS-DERIVED remap: present bytes -> 1,2,3,... in increasing byte order, 256-entry bijection,
END has no code. A universal table cannot satisfy this (it fails on any corpus with a smaller
alphabet; we hit it on a 428-byte fixture).

Consequence, stated precisely:
  the 150 MB END-format container  IS proven (G4: 100/100 patterns, counts AND positions exact)
  but it was built with a hand-derived remap passed OUTSIDE xsa build.
  Therefore: shipping tree = proven container, NOT yet a runnable command.
