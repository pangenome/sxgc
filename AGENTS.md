# Tape Reader working agreement

Work in the `main` checkout (`~/sxgc`); commit verified changes and receipts to `main` and push to `origin/main`. Historical lanes are evidence, not the integration target. Do not remove other worktrees or rewrite their history.

For any builder task, read **[TAPE_VISION.md](TAPE_VISION.md) first**. It defines the operator-approved algorithm and distinguishes the target from working prototypes. History, a passing checksum, a faster baseline, or the name of a binary cannot amend that design. If the task appears to require changing the sort unit, the PFP/order invariant, the resource law, or the public entry point, report the conflict and ask the operator before implementing an alternative.

Bound each construction task (including delegated tasks): name the phase, input/output units, allowed files, forbidden work, and the smallest test that can disprove it. Review **what the code actually sorts or scans** separately from output correctness and speed. Keep expensive checks in qualification. Record gaps as gaps; do not add an engine, launch a larger run, or change a default to make a task pass.

Aim for **under 2×** the resident wall time per input byte; require **under 3×** for performance promotion at matching phase boundaries, product profile and verification. An old under-10× safety check is not the new goal. Measure physical/attributed traffic and access locality separately; speed parity alone does not establish an IO saving. State the baseline, RAM/swap/CPU grants, scratch, and timings from raw input vs from prepared columns separately. Do not promote a larger rung merely because the cap was respected.

Within an authorized study, a failed gate is evidence: preserve the receipt, diagnose the limiting mechanism, and take the next safe step within scope. An operator stop or request for discussion is not authority to launch a replacement. Never treat a running but stranded worker as useful progress. Respect cooperative stops and the existing resource/scale gates; if blocked on a production arm, study independently on small inputs instead.

When the implementation path is unclear, run a theoretical study: state the invariant, cost model, assumptions and counterexamples, derive a falsifiable prediction, then test it empirically. Long-running, bounded studies are appropriate. Use well-distributed small corpus samples to probe the same access pattern; match working-set/cache and batch/input ratios, check skew and phase-specific behavior across sizes, and distinguish modeled misses from physical IO. Report what transfers and what remains unproven.
