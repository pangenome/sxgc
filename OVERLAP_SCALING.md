# Scaling gate on main: strictly below 10×, not just below the RAM cap

Use `~/sxgc` on `main`. Historical lanes and their private products are immutable references. Baseline: `gates/receipts/resident-1g`, cold prepared `parse.u32` + `dictionary.refs` through a finished v8 index, all rows externally audited. **465.6692705 s for 1,000,000,665 bytes.** For the same workload the strict wall limit is 4,656.692705 s, not a target to consume. For changed N compare `(wall/N)/(baseline_wall/baseline_N)` and report absolute throughput as well. If a same-size resident build is possible, compare at the same N too. The 96-minute external stream from *later* prepared columns already costs more than this limit before finish; it is an oracle/fallback, not the throughput plan. Raw parse preparation, cold copies, oracle resources and post-run certification are separate; don't call this a raw-input speed guarantee. A different member profile or verification scope needs a new baseline.

## First obstacle: dictionary width, not parse RAM

At the verified rung the encoded dictionary D=1,166,209,205 positions vs m=31,784,026 parse positions. Just the narrow dictionary SA + dense owner cost 8D bytes, one random-access u32 owner for every byte including overlap. Naively doubling both to 64-bit positions wastes memory; widening the parse is unrelated. Use `bash gates/overlap_resident_gate.sh wide` to compare a pinned wide byte-dictionary API, u64 word starts, but still narrow phrase IDs/word offsets/parse ranks. The same full oracle checks, finish, input, 20 GiB shared hard cap / no swap, 14 GiB producer array grant, 4 CPU quota; separately capped 1,400 MiB / 1 CPU raw verifier. No changes to the frozen finish and no new on-disk sort columns. The 1 GB corpus and current narrow output widths remain explicit guards.

Invariant: an encoded position's enclosing word is `rank(start_bits, pos inclusive) - 1`. Its finite tail contributes only if its length excluding SEP is >8 (nonfinal) or >1 (EOF word includes END). A 16-byte block/64 positions holds a start mask and the number of preceding starts. Use one popcount; handle the empty blocks inside long words. Subtract the **wide start first**, narrow only the proved word-local difference. Predicted owner size at rung1: 291,552,304 B instead of 4,664,836,820 B. Including dictionary bytes, SA and owner, this moves the coefficient from `9D` to `9.25D`, not `13D`; add starts, lists, RMQ, bounded heap, buffers and finish separately. This is a width solution, still O(D) RAM. Test block boundaries, many starts in one block, long gaps, `2^31`, `2^32` and high absolute coordinates; verify actual container SHA. For small lengths the upstream 64-bit interface calls its narrow kernel internally. The next *actual* native-wide sort needs its own gate.

## When the live-set estimate fails

1. **Census first.** Count N, m, k, actual D, used alphabet, longest span and occurrence-weighted mass per lexical range; forecast the simultaneous array lifetimes, kernel buffers, consumers, heap growth and transient copies. Do not reserve against machine `MemAvailable`. Keep global ranks, text offsets and LCP bounds wide where required, otherwise use checked shard-local offsets. A fit below `INT32_MAX` is not a fit below a memory grant, or vice versa.
2. **Spend memory to eliminate whole traversals.** Keep the many-to-one rank/occurrence joins resident when they fit. If D alone fails, first try bounded *lexical ranges* of dictionary tails, materialized from local word bytes, with equal tails kept together and LCP carried across ranges. Admit ranges by **bytes and occurrence mass**, not descriptor count. Reject plans that scan the dictionary once per tiny window or write copies of all suffix strings: at this rung full copied keys would be ~41 GB. For an outlier recursively refine just that range or stream a k-way merge of its sorted occurrence lists. Range routing or partition-local bytes are **proposed** until measured, not a claim of bounded passes on all inputs. A chunk-SA merge that retains 4D bytes of runs on disk is not compatible with a blanket 2N scratch law.
3. **Recurse only if m and its workspace fail.** On this parse the second level is 31× shorter, yet owns 99.7% as many lower-level token offsets as m; budget induction as well as the top sort. No reliance on run compression (90% as many P1 BWT runs as tokens). A 64-bit dictionary gate says nothing about wide parse ranks or the row transport. Before crossing 4 GiB of *text*, gate wide corpus offsets, suffix positions, LCP, END, oracle and sink together.
4. **Reject unproductive work early.** Plan total routed/read/written bytes per batch and source scans. Include compression ratio, skew and physical read amplification on cold input; bandwidth alone is not a wall model for pointer-heavy sorts. Measure isolated phase times **and overlapping pipeline wall time** including backpressure. A proposed out-of-core profile must earn its <10× result with a cold full-stream comparison at the same `workspace/input` and `batch/input` ratios before promotion. Enforce memory/swap, the 2N live scratch limit, read/time stops and independent product identity separately. Use a slower emergency fallback only as an explicitly labeled exception, not a performance pass.

Next rungs: wide-interface parity at 1 GB → actual-width and censused memory/throughput at 3 GB → 10 GB exact product before 100 GB. Qualify raw-to-product preparation and the 100 GB member profile separately. No 100 GB rehearsal or Pile run implied.
