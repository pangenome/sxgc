# Scaling gate on main: target <2×; promotion <3×, not just a RAM pass

Use `~/sxgc` on `main`. Historical lanes and their private products are immutable references. Baseline: `gates/receipts/resident-1g`, cold prepared `parse.u32` + `dictionary.refs` through a finished v8 index, all rows externally audited. **465.6692705 s for 1,000,000,665 bytes.** For the same workload aim below **931.339 s (2×)** and require **below 1,397.008 s (3×)** for promotion. Keep the original 4,656.693 s (10×) ceiling only as a historical comparison. Separately demonstrate any claimed saving in disk writes/reads or random accesses: changing width alone need not save IO. For changed N compare `(wall/N)/(baseline_wall/baseline_N)` and report absolute throughput as well. If a same-size resident build is possible, compare at the same N too. The 96-minute external stream from *later* prepared columns already costs more than this limit before finish; it is an oracle/fallback, not the throughput plan. Raw parse preparation, cold copies, oracle resources and post-run certification are separate; don't call this a raw-input speed guarantee. A different member profile or verification scope needs a new baseline.

## First obstacle: dictionary width, not parse RAM

At the verified rung the encoded dictionary D=1,166,209,205 positions vs m=31,784,026 parse positions. Just the narrow dictionary SA + dense owner cost 8D bytes, one random-access u32 owner for every byte including overlap. Naively doubling both to 64-bit positions wastes memory; widening the parse is unrelated. Use `bash gates/overlap_resident_gate.sh wide` to compare a pinned wide byte-dictionary API, u64 word starts, but still narrow phrase IDs/word offsets/parse ranks. The same full oracle checks, finish, input, 20 GiB shared hard cap / no swap, 14 GiB producer array grant, 4 CPU quota; separately capped 1,400 MiB / 1 CPU raw verifier. No changes to the frozen finish and no new on-disk sort columns. The 1 GB corpus and current narrow output widths remain explicit guards.

Invariant: an encoded position's enclosing word is `rank(start_bits, pos inclusive) - 1`. Its finite tail contributes only if its length excluding SEP is >8 (nonfinal) or >1 (EOF word includes END). A 16-byte block/64 positions holds a start mask and the number of preceding starts. Use one popcount; handle the empty blocks inside long words. Subtract the **wide start first**, narrow only the proved word-local difference. Predicted owner size at rung1: 291,552,304 B instead of 4,664,836,820 B. Including dictionary bytes, SA and owner, this moves the coefficient from `9D` to `9.25D`, not `13D`; add starts, lists, RMQ, bounded heap, buffers and finish separately. This is a width solution, still O(D) RAM. Test block boundaries, many starts in one block, long gaps, `2^31`, `2^32` and high absolute coordinates; verify actual container SHA. For small lengths the upstream 64-bit interface calls its narrow kernel internally. The next *actual* native-wide sort needs its own gate.

**1 GB wide-interface full product passed** (`resident-rung1-wide-ali8cD`, binary `0b5b178`, [receipt](gates/receipts/resident-wide-1g/summary.md)). All ranks and 1,000,000,666 rows verified, expected SHA and nine-member profile. 561.796 s vs 465.669 s (**1.2064×**), 13.526 GiB shared peak / 20 GiB, no swap/OOM. Producer wrote a 64-bit SA only in RAM. Owner index 291,552,304 B, starts 202,693,280 B; disk reads during sorts and emission zero. 1.457 GB build-worker attributed reads and 9.661 GB writes vs 1.457/9.290 GB narrow. Audit pipe writes occupied 158.89 s vs 77.33 s, so not all the wall difference is sort CPU. **Speed pass, not a disk reduction.** No receipt claiming a 2×/3× result at larger N or nonresident-D ratios.

## Physically rewriting the corpus as the parse

This is not just an array of pointers. The checked external lexical parse writes `parse.u32` in text order. The baseline starts *after that step*: the indexer reads IDs, ranks their suffixes, and consults the original bytes only in packing the distinct dictionary and gathering phrase-start predecessor bytes. The frozen finish and the independent raw verifier retain their own corpus input. Neither the 127 MB first parse nor the 4 MB second parse alone is a lossless replacement for all the text.

`gates/overlap_lexparse.cpp --packed` is an alternative front-end output mode. When assigning lexical IDs from the bounded sorted buckets, write `dictionary.packed`: for each distinct ID, u32 LE raw length with the high bit tagging the sole EOF word, then the complete raw overlapping word. No reference or adjacency output. The physical `parse.u32` assignments are unchanged. It doesn't take another pass through the raw corpus: the word is already in the dedup bucket. A newly emitted word costs `4+len` bytes, and its ordinal assignment costs 8; they replace a retired `12+len` bucket record. A duplicate writes just the 8-byte assignment. Ordinal scatter replaces 8-byte assignments with 4-byte parse IDs. The disk cap is checked as files are produced/retired.

Standalone `bash gates/overlap_packed_gate.sh` checks this front end from raw 1 GB input in 192 MiB/no swap, then compares parse IDs byte-for-byte with the banked stream. A new process reads only the two cold columns sequentially, keeping word bytes explicitly resident for its RAM lookups. For each ID, emit the owned stride (`raw_len-8` before EOF, entire raw length on EOF). The last byte **owned**, not the last byte stored, is the predecessor at the following phrase start. Compare complete reconstructed-text SHA and SHA of all `(start,predecessor)` pairs including END with an independent raw-text trigger scan. No decoded-text, SA, LCP or triples file. This checks the representation; the frozen finish has not been made corpus-free. A disk-saving claim for the full path must also address the sink pieces, LCP slices and finish spools; their consumption/durability contracts matter.

**Packed representation passed** (`packed-parse-ORX2dw`, [receipt](gates/receipts/packed-parse-1g/verdict.log)). From 1,000,000,665 raw bytes: 30.38 s in the 192 MiB lexparse service, 1,635,681,177 B counted peak, 3,861,856,256 attributed read bytes. `parse.u32`=127,136,104 B; `dictionary.packed`=1,242,219,181 B; **together 1,369,355,285 B**, not 127 MB. The decoder opened only those two columns, read 1,369,362,432 device-attributed bytes and wrote zero, in 6.92 s. Verified 31,784,025 overlaps plus original text SHA `c382daa53d0e66fdc921c32d356961b7e8189ceee0a435bb3b66e06b203ebb61` and every phrase-start predecessor including virtual END against a separate raw scan. This is not a packed-input container verdict. The reference layout's corpus + refs + IDs is 1,329,830,041 B; packing improves locality/independence, not total storage on this sample. The full container timings use the reference layout and exclude this front end.

## Spend bounded RAM on transient IO, not the durable result

`bash gates/overlap_resident_gate.sh wide-handoff` holds all inputs, wide sort, frozen finish, separate oracle, quotas and hard caps fixed against `wide`. Only piece files and LCP slices use a **fresh private tmpfs**; the producer publishes the same bytes/markers and the finish returns the same credits. Keep prepared parse, corpus, PFCK/bitmap/m14 spools and the final fsynced container on NVMe. Both live RAM and logical scratch charge the volatile backlog; cap it by 32 outstanding pieces + release batch/frontier slack, 64 slices at worst-case all escapes and control margin. Monitor private allocated and logical bytes, cgroup shmem, total cgroup peak and both raw worker IO counters. The queue size is controlled by the windows, not by storing an all-row triples file. This is opt-in and **not a resumable mid-sweep mode**: a lost tmpfs is replayed from the retained durable inputs; never claim `fsync` of a tmpfs file makes it crash durable. Require the same full SHA and row oracle, <3× baseline wall (aim <2×), **≤0.50× build-worker attributed writes and ≤1.05× reads** vs the matched wide-disk gate. Those are measured byte counters, not block-device seek counts.

**Matched 1 GB handoff gate: PASS** (`148e54d`, `resident-rung1-wide-handoff-YstLTd`, [phase table](gates/receipts/resident-handoff-1g/summary.md), [goals](gates/receipts/resident-handoff-1g/goals.json)). Every parse rank and all 1,000,000,666 rows checked; identical nine-member container SHA. From prepared IDs/refs the wall was **429.375 s** vs 561.796 s wide-on-disk and 465.669 s narrow baseline. Build-worker writes fell from **9.661 GB to 3.296 GB** (−65.9% vs matched wide); reads remained ~1.457 GB. Sink writes fell from ~5.87 GB to ~1 MB; nearly all remaining attributed writes are in the frozen finish. Shared cgroup peak **13.522 GiB / 20 GiB**, no swap or OOM. Private tmpfs allocation peaked at 58,073,088 B sampled (cgroup shmem 58,900,480 B sampled), vs 378,809,888 B reserved. Joint counted scratch 1,119,200,658 B sampled vs 1,597,106,334 B reserved / 2,000,001,330 B maximum. The exact product and IO reduction are established on this input. Wall includes verifier backpressure (audit writes 80.30 s here vs 158.89 s wide-on-disk); do not attribute the entire wall improvement to avoiding disk writes. No block-seek or packed-input product claim. Next join the independently checked packed-word front end to the producer and cost its raw-to-product wall and scratch lifetimes.

## When the live-set estimate fails

1. **Census first.** Count N, m, k, actual D, used alphabet, longest span and occurrence-weighted mass per lexical range; forecast the simultaneous array lifetimes, kernel buffers, consumers, heap growth and transient copies. Do not reserve against machine `MemAvailable`. Keep global ranks, text offsets and LCP bounds wide where required, otherwise use checked shard-local offsets. A fit below `INT32_MAX` is not a fit below a memory grant, or vice versa.
2. **Spend memory to eliminate whole traversals.** Keep the many-to-one rank/occurrence joins resident when they fit. If D alone fails, first try bounded *lexical ranges* of dictionary tails, materialized from local word bytes, with equal tails kept together and LCP carried across ranges. Admit ranges by **bytes and occurrence mass**, not descriptor count. Reject plans that scan the dictionary once per tiny window or write copies of all suffix strings: at this rung full copied keys would be ~41 GB. For an outlier recursively refine just that range or stream a k-way merge of its sorted occurrence lists. Range routing or partition-local bytes are **proposed** until measured, not a claim of bounded passes on all inputs. A chunk-SA merge that retains 4D bytes of runs on disk is not compatible with a blanket 2N scratch law.
3. **Recurse only if m and its workspace fail.** On this parse the second level is 31× shorter, yet owns 99.7% as many lower-level token offsets as m; budget induction as well as the top sort. No reliance on run compression (90% as many P1 BWT runs as tokens). A 64-bit dictionary gate says nothing about wide parse ranks or the row transport. Before crossing 4 GiB of *text*, gate wide corpus offsets, suffix positions, LCP, END, oracle and sink together.
4. **Reject unproductive work early.** Plan total routed/read/written bytes per batch and source scans. Include compression ratio, skew and physical read amplification on cold input; bandwidth alone is not a wall model for pointer-heavy sorts. Measure isolated phase times **and overlapping pipeline wall time** including backpressure. A proposed out-of-core profile must earn its <3× result with a cold full-stream comparison at the same `workspace/input` and `batch/input` ratios before promotion. Enforce memory/swap, the 2N live scratch limit, read/time stops and independent product identity separately. Use a slower emergency fallback only as an explicitly labeled exception, not a performance pass.

### A middle ground between the full dictionary SA and disk windows

`gates/overlap_range_fit.py` reads the existing **exact** 3,340-interval plan (542,645 B), not the corpus. Pack adjacent whole intervals greedily into a fixed RAM arena; if a single interval exceeds it, refuse or refine, never split an equal tail. Every output row is accounted for; this models distribution/storage, not elapsed time. On the 1 GB counts, keeping only the dictionary bytes, u64 starts, occurrence CSR and aligned RMQ resident costs 1,899,333,479 B. An 8-byte `(word_id,offset)` generated in physical order needs no dictionary-position SA or dense owner; comparison may follow the pointer **only because the dictionary is charged as resident**. The largest possible merge heap on this plan reserves another 10,485,760 B (largest unsplit interval as an upper bound). With a 1 GiB arena the resulting emit arrays are ~2.98 GB; preparation, finish, control/buffers, page cache and safety margin still need their own simultaneous budget.

| Payload per descriptor | Whole-dictionary distributions, 1 GiB arena | 256 MiB arena |
|---|---:|---:|
| 8-byte local ref | **7** | 29 |
| 16-byte record (e.g. ref + early prefix) | 15 | 57 |
| 16-byte record + whole tail bytes | 53 | 216 |

[Exact packing receipt](gates/receipts/resident-range-fit/fit.json); run `python3 gates/overlap_range_fit.py /mnt/nvme2n1/erikg/TAPEREADER/sandbox/all-rung1-6wQTZX/in/plan`. Seven distributions mean 8.16 GB of **logical in-memory** dictionary traversal; these are not seven physical reads, nor seven-times wall time. They exclude the exact histogram/planner pass and ordering work. Sorting pointers inside a charged resident dictionary can still be CPU/cache expensive, so time representative ranges (including skew and long common prefixes) and then a full, verified build before declaring <3×. A physically nonresident dictionary requires a different profile with coalesced local byte staging and batched occurrence gathers charged to both IO and scratch. Neither this model nor the wide-ABI control certifies it.

## Integrated raw → packed columns → product gate

Run `bash gates/overlap_resident_gate.sh packed-raw`. Start with the private cold corpus/remap, not prepared refs or parse IDs. In the metered build service, create a **new** `columns/` using the external lexical parser; it charges live scratch before writes. Cold-check only the new columns and private corpus at the transition so cache hits from preparation cannot hide the consumer's IO. The resident producer receives that column directory (no raw text or refs), validates lexical records/overlap edges, derives N from the text-order parse, and carries the previous word's last *owned* byte into lists. Original text is still an input to lexparse, the frozen sink/finish and the separate oracle. Check-only inverse ranks never supply producer state. All existing 1 GB width/size caps still apply.

**Lifetimes:** no finish spools during lexparse (2N hard scratch guard) or column load. Keep the 1.369 GB of columns through dictionary construction, then unlink **only this run's generated dictionary tape**, after the producer has closed it and before starting sink/finish. The 127 MB parse remains charged. The finish phase reserves its full spools and bounded volatile handoff as before. Do not add peaks of mutually exclusive stages, exclude a generated tape as if it were free input, or delete a banked tape. Recovery of this profile is from raw input, not from a lost volatile handoff. Predict identical ranks, triples and final SHA; compare timing at the prepared-column boundary for <2×/<3×. Separately time raw to published container including lexparse and the private cold transition, aggregate front-end + post-front-end worker IO, and keep oracle resources/post-run certification separate. No earlier matched raw-to-product baseline is assumed.

### Bounded one-file placement hypothesis (before the repeat)

The frozen finish sets text-position bits at scattered offsets of the shared writable `prefix.chi-bitmap`, size `B=ceil(rows/8)`. It keeps setting bits until the end of the sweep. If most pages are dirtied within a background-writeback period `T`, expect extra dirty-page traffic of order `B × emission_seconds / T`, **not** `B` once per build. This machine reports dirty expiry 30 s, writeback wakeup 5 s; don't change either knob. On the four banked 1 GB arms, `(finish.write_bytes - finish.wchar)/B` ranges 9.27–13.24 bitmap equivalents, or one per 33–37 emit seconds. On 3 GB it is 41.59 equivalents, one per 32.28 s. At T=30 s the 3 GB model gives ~16.78 GB extra; difference measured ~15.60 GB. This is a diagnostic, **not file-level accounting**: `wchar` includes nondisk writes and page attribution, metadata, cancelation, writeback scheduling and sparse access can all change the difference. A clustered update stream, fitting inside one writeback interval, or a different mapped file could falsify the inference.

**Matched prediction:** keep the fresh raw/packed run, both CPU quotas, all memory/scratch grants, persistence of other spools, oracle and frozen finish identical. Change only where that one mapped file is created. Charge the full 375,000,001 B bitmap in the private no-swap tmpfs grant and still count it once toward live scratch. Do not resume a lost volatile sweep. If the dirty bitmap dominates, prepared build-worker writes should fall from 21.912 GB to roughly 6–8 GB (require ≤10.956 GB, i.e. 0.5× matched 3 GB control), with ≤1.05× reads; still require the original normalized IO and speed scores and exact independent row and container checks. Report raw IO including the unchanged parser separately; it is not expected to shrink by the same fraction. This bitmap scales with text length, and RAM availability must be rechecked at larger sizes.

`bash gates/overlap_three_gate.sh ram-bitmap` runs this one-variable arm. `gates/finish_bitmap_tmpfs.c` is an opt-in gate-only pathname adapter, not a change to the finish algorithm or binary: its single exact `frag.chi-bitmap` create/unlink pair uses an inherited fd for an empty mode-0700 private tmpfs directory. No mmap, fsync, rename, output or row operations are simulated. The test checks exclusivity (including a preexisting disk source), neighbor files, mmap visibility, cleanup and invalid-fd refusal. Require the full bitmap size observed only in tmpfs, create + unlink exactly once, same hashes for all original executables/remap, no change in counted logical reservation, same row oracle and nine-member identity. A positive score establishes an IO saving at this grant, not a claim about individual block seeks, nor a cheaper way to recover an interrupted sweep.

**Matched bitmap PASS** (`6e32ed6`, `packed-3g-bitmap-qNujiV`, [receipts](gates/receipts/packed-3g-bitmap/summary.md)). Original producer, sink, verifier, remap and finish hashes identical to control; exact 3,000,000,001 rows and container SHA. Post-front worker writes **21.912 → 5.408 GB** (0.247×, even below the predicted 6–8 GB), reads **7.047 GB unchanged**. Recheck that reservation before using this placement at any larger rung.

### 10 GB: real column census before allocating sort arrays

`bash gates/overlap_ten_front.sh` is the **standalone packed front only** (192 MiB, one CPU, no swap, 2N live scratch), gated on the matched 3 GB SHA/IO pass. On private cold `pf-10gb.txt`, scan corpus offsets in u64 but store no corpus pointer in lexical buckets: each occurrence already carries its full payload, so only `(span/EOF, occurrence ID)` is needed. Preserve the original text-order u32 parse and lexical packed tape format. 1,024 sampled lexical buckets, hard 64 MiB/2M-occurrence limits, credit each file before writes and retire buckets before replacement. Worst-case logical bound after dedup/assignment is `N + 20*m` (raw bytes + overlaps + tag + assignments); refuse if it exceeds 2N. The front records actual wide starts, D, m, k, alphabet, signed `m+6k` extent, traffic and measured scratch, and **models** a wide text/LCP consumer; it does not allocate it. Six small byte-for-byte oracle cases and rung/reuse/stop refusals precede the real census. A successful census is not a 10 GB suffix order, decoded text SHA, or container verdict.

**10 GB census PASS** (`fd9960d`, `packed-front-10g-YebiCY`, [receipt](gates/receipts/packed-front-10g/front-end.json)): 357.757 s, 37.612 GB read / 33.635 GB written, no swap or OOM. m=318,164,488, k=234,472,723, `m+6k=1,725,000,826` fits signed i32. D=11,239,544,612; both the 11.943 GB word tape and 181,581,998 occurrence starts exceed u32 addressing. Alphabet=243; longest word 88,468 B. Counted peak 15,090,631,800 B / 20 GB vs 30.647 GB whole directory allocated (includes private copy, FS blocks and control files). Largest proposed resident array set **123.166 GB (114.71 GiB)**; this is a plan from a measured census, not measured sort RSS or a product verdict.

**Wide row transport, still 12 bytes:** the explicit 10 GB sink and independent `overlap_row43_oracle.cpp` accept LE low u32 text offset, low u32 byte LCP, and a third u32 `[tag=1:1 | high LCP:11 | high offset:11 | BWT:9]`. This avoids increasing pipe volume to two 64-bit words plus a predecessor. Both coordinates are strictly below 2^43, predecessor is 0..256. Old/new formats reject one another via the tag; 1/3 GB still use original untagged triples. Rust encoder/decoder boundary tests span 2^32, 10 GB and the 43-bit ceiling. Seven small independent full row streams check the separate C++ raw verifier, including bad high bits, END, EOF, exact adjacent ordering/LCP, predecessor and final rank. These tests alone are **not** a 10 GB row producer or product. Rerun past byte-identical binary A/Bs at their recorded commits.
